# Build-out: from a document section to a merged change

This is how work moves through Mycelium, from the specification to the
standing mesh. [AGENTS.md](AGENTS.md) holds the working rules and
[CONTRIBUTING.md](CONTRIBUTING.md) the process. This file holds the order
in which an item is built, and the gates it passes.

## 1. The chain

| Step | Where it lives | What it holds |
|---|---|---|
| Document section | `docs/` (a governing document or a proposal in `docs/proposals/`) | The claim as algebra: formulas, refusals by name, joint-read fixtures where kernels share it |
| Ruling | A labelled comment on the issue, recorded in the proposal's *Ruled* section | Who ruled, when, and what. A change to the network contract (the Concordance, the wire, the ledger layout, a law version) needs the operator's ruling |
| Milestone | GitHub milestones | A build-out phase named by what it delivers, its design documents and its done-when in the description |
| Issue | GitHub issues, on the project [Mycelium](https://github.com/orgs/SAIOS-SAMN/projects/2) | One item: the section it builds (the project's *Doc* field), its done-when as a test or a live reading, its milestone, its *Area* and its *Seam* |
| Branch | One `git worktree` and branch per item | The claims first, then the code |
| Pull request | Names the issue (`Closes #N`) | The change, its tests, its documents and a changelog fragment under `changes/`; the two checks; the live reading |
| Merge | `main` | After green CI, the live reading and, for the network contract, the operator's approval |

## 2. The gates

1. **Formulas before code.** The section states the claim as algebra
   (MU-STANDARDS 3.1) before any code is written. A design question the
   specification does not settle is asked on the issue and ruled, never
   decided in code.
2. **Witnesses.** The claims become tests, a `compile_fail` doc test where
   a guard type makes the wrong structure unwritable. The two checks of
   [AGENTS › Checks](AGENTS.md#checks) pass on the branch with `main`
   merged in.
3. **Reads.** A change passes only once it is live on the standing mesh
   (three hyphae on ports 8500–8502, minds working). The issue names the live
   reading it expects, and the pull request records the reading it got: a
   log line, an observer table or a peer kernel's own read. CI is no
   substitute for it.
4. **Network contract.** A change to the wire, the ledger layout, a law
   version or the Concordance is stated under *Network contract* in the
   pull request, with the operator's approval cited.

## 3. The project's fields

- **Status:** Todo, In progress, Blocked (waiting on a ruling or another
  item), Done.
- **Milestone:** the build-out phase.
- **Area:** server, client, economy, chronometry, laws, transport, docs,
  release.
- **Doc:** the section that governs the item, for example `78.184 §5` or
  `MU-SENSING §3.7`.
- **Seam:** none, netstratum or xylarium, for the peer kernel that shares
  the item.

## 4. Across kernels

An item shared with a peer kernel (netstratum, xylarium) carries the
`cross-project` label and links the other repository's issue, on both
sides. A shared form is ruled once, by the one operator, for every kernel.
Its fixtures are read by each kernel in its own code before the form is
served.

## 5. Keeping it current

- An issue that is done is closed by the pull request that did it. One
  that is superseded is closed with a link to its successor.
- [ROADMAP › Now](ROADMAP.md#now) lists the order of work. It is
  rewritten, not appended to, and names no closed issue as open.
- A branch is deleted once its pull request is merged or closed.
