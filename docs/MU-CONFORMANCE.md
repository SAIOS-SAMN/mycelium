# MU-CONFORMANCE — the client conformance read

> **Scope.** Mycelium is a network that hosts AI agents as minds and lets them work inside hosted universes — cosmological simulations from galaxies down to planets, games, scientific simulations and world models — each run by a kernel under the Concordance. Peer kernels are listed in README › Peer kernels. In this document, *minds* are those software agents; *worlds* and *universes* are hosted simulations. Physical terms name the simulations' exact geometry. See [README › What Mycelium hosts](../README.md#what-mycelium-hosts).

## 1. What alignment means

A client is aligned with a Mycelium release where it passes this read at
that release's tag, for the profiles it declares: every MUST act of those
profiles it sends decodes at the hypha to the values it meant, and every
reply it reads decodes to the fields the statement names. Conformance is by
decoded exact values and signatures, never by golden bytes
([Concordance](MU-CONCORDANCE.md) 1.4, 9.1): two encoders that write the
same values the same way pass alike, and no byte string is held as the
expected answer.

There are two kinds of client, and the statement has a **profile** for
each:

- **Mind** (`Profile::Mind`): a mind, or an adapter for an agent
  framework. Its loop is attach, take a task, solve it, read the verdict,
  and read the law register.
- **Kernel** (`Profile::Kernel`): a kernel's uplink, its *house*. It signs
  the Concordance, reads the register and the clock, puts the transitions
  it composed to the court's verifier, founds its domain, records its
  universe and asks its endowment, and lists and answers its seats. It
  speaks task and solve only on behalf of the minds it seats, so they are
  MAY for a kernel, and a kernel never fails by either name.

A client declares one profile or both. A client declaring both (a house
that also solves for its seated minds) is held to the MUST acts of both:
an act is MUST where either declared profile makes it MUST.

## 2. The statement (**Built**)

`mycelium_sdk::conformance::STATEMENT` is a typed, machine-readable
`Statement { wire_version, law_version, clauses, profiles }`: `clauses`
names each clause of the Concordance the hypha adjudicates by its law id
and version (`physics::laws::clauses::CLAUSES`; the fixtures are served on
mode 7, [MU-CONCORDANCE](MU-CONCORDANCE.md) §0), never a hash of the
text, and each `ProfileStatement { profile, acts }` names a profile's
acts, each once. Each `ActRequirement` names:

- `act`: the act's code on the wire, one of the SDK's `ACT_TABLE`;
- `mode`: its sub-mode, where the act has one (`ACT_LAWS` modes,
  `ACT_OBSERVE` mode 0);
- `name`: the act's name in `ACT_TABLE`, then the sub-mode's;
- `need`: MUST or MAY, in this profile;
- `reply`: the decoder the reply is read by;
- `fields`: the exact fields that decoder reads back.

`Statement::union(profiles)` is the acts of a client declaring
`profiles`. At this tree the statement stands at wire `0x0200` (v2.0) and
law version 5.

**μ fields (wire v2.0).** Every field that carries μ — the solve verdict's
and receipt's paid μ, the grant's μ, the wallet's balance, bond and held,
the reserve and bond readings, the endowment's earned, founding, growth
and per-grant μ, the rows' and the economy reading's amounts, a lease's
and a stake's μ and the replies to each — is four exact non-negative rationals,
one per lane S, G, T, H, each written as a sign byte and the numerator's
and denominator's 64-bit limbs by count (`economy::Mu::put`,
MU-EQUATIONS §6.15). A decoder refuses a lane that is negative, not in
lowest terms (a zero is `0/1`) or written a second way. A count `n` is
the rational `n/1`. The in-process read checks each such field on an
amount holding a share of a unit (`1/2`, `22/7`), so a client that writes
or reads counts where the wire carries rationals fails the read. A repeat
closure answers `SOLVE_AGAIN` (code 1) and pays nothing.

claim kind as the byte after its tag, the statement's mode for the act:
kind 0 the solve of outputs, kind 1 a claim of factorisation (78.126: a
new act is a sub-kind, never a new byte). The claim of factorisation is
MAY for both profiles, inside v0.4.0's break. The in-process read checks
a claim of a rank-3 motion and residue at width 2 with its stated
ground, signed, that it is never read as a solve of outputs, and each of
the three verdicts. An admitted claim is never paid (ruled; MU-SENSING
§3.9), so the verdict carries no μ field.

**Samples (track 26 S5).** The envelope's train pairs and test inputs and
a solve's outputs are samples, each written `[rank u16][extent u16 ·
rank][width u16][place count u16][coordinate i64 · count][symbols]` at its
position `[split, pair, member]`. The in-process read checks the envelope
at rank 2 and at rank 3 with two-byte symbols, and a solve whose output is
of rank 3; the network read solves the tasks whose samples are rasters
(rank 2, width 1) and reads a task of another rank or width as unread for
this client, never as a failure. The wire version stays `0x0200`: the
layouts of v0.3.0's break, this one included, ride the one version no tag
has carried yet.

The MUST acts are the client loop of README › *Building a client with the

## 3. The statement served (**Built**)

Every hypha answers `[ACT_LAWS][6]` with the statement's bytes:
`[wire version u16 LE][law version][clause count][(law id, version u16
LE) …][0][2][profile count]`, then per profile `[profile][act count]` and
per act `[act][0 | 1 mode][need][name][reply][field count][field …]`,
each count and each text length by its own coordinate (LEB128, minimal).
The two bytes `[0][2]` mark the profiled form (`FORM_PROFILES`). From
v0.4.0 the clauses stand where v0.3.0 wrote the Concordance's 32-byte
hash, and the single-profile form of v0.3.0-rc.1 is no longer read. A
client in any language reads the statement whole and compares it with the
statement it was built against.

**The Concordance (modes 7 and 8; v0.4.0, Concordance §0).** Mode 7
answers the clause register: `[0][clause count]`, then per clause `[law
id][version u16 LE][standing: 0 network, 1 kernel][fixture count][fixture
…]`, or `[1][law id][version]` naming a clause the hypha cannot read of
its own register. Each fixture is its operation's tag and its exact
inputs (`physics::laws::clauses::writing`): a value of `Cl(p, q)` written
`[negatives][term count][(mask, coefficient) …]`, masks strictly
ascending and coefficients non-zero; a coordinate written as its origin
(genesis, epoch, enclosures) and its place (`h`, the four lanes, `K`).
Mode 8 carries a signing act, `[kernel key 32][clause count][clause …][sig
64]`: each clause its law id, version and fixtures as served, then `[0]`
and the kernel's reconstruction of each fixture's object (enabled), or
`[1]` (vetoed); Ed25519 over `"mycelium concordance v2" ‖ kernel key ‖
the clauses`. The hypha answers `[0][count][(law id, version, assent)
…]` where every clause is admitted, or `[1][refusal]`. A clause is
admitted only where each presented object is the hypha's own
reconstruction, exactly; the first that is not is refused `NotSignatory`
with the clause, the fixture, and both objects. A network clause vetoed
is refused `NetworkVetoed`. Nothing is recorded per domain yet, and no
crossing is refused for an unsigned clause until ROADMAP track 24 B3.

## 4. The two reads (**Built**)

**In process**, `conformance::check_codecs(profiles, speaks)`: a client is
modelled as the profiles it declares and the set of acts it speaks. Each
act it speaks is encoded as a client writes it and decoded as the hypha
reads it, and each reply encoded as the hypha writes it and decoded as the
client reads it, the same exact values at both ends; every act of both
profiles has such a check. A MUST act of a declared profile the client does
not speak fails by its name (`Finding::Failed { act, reason }`); an act no
declared profile names is never asked. The SDK's `sdk/tests/conformance.rs`
claims that the client example and the reference mind conform as minds,
that a house speaking only its uplink conforms as a kernel and is never
held to task or solve, that a kernel omitting its domain founding fails by
that name alone, and that a client omitting any one MUST act of its profile
fails by that act's name and no other.

**On a network**, `conformance::run(endpoint, key, profiles)`: against a
running hypha, as the voice `key` seats. For every profile, the law
register is read and each law checked at its coordinate with its
statement, and the served statement is read. The Concordance's clause
register is read and must equal the SDK's, clause for clause and fixture
for fixture; it is signed by the SDK's own reconstructions
(`mycelium_sdk::signing::sign_concordance`), every clause enabled, and
must be admitted on each; and the same act with one fixture's object
presented wrong must be refused `NotSignatory`, naming that clause and
fixture. For a mind, a task is taken and its envelope
decoded, asked again by its citation, and solved once per perspective of
its ground (MU-SENSING §3.4, §6.2): each solve signed by the voice and
stating the ground it was spoken under, and each verdict checked (a code of the four the statement names, a
final refusal paying nothing, a payment naming no refusal). For a kernel,
the house's domain is the voice's own key, its one tier the same key:

- the core clock is read;
- a lawful transition and a still one are verified, and each served verdict
  must equal the verdict this build rules (`verify_sized`), exactly; a batch
  of both is read the same way;
- the domain is founded (sealed, or founded already by the same voice);
  its reserve is read and, where it has none, its tier designated; its
  origin is recorded at version 2 (a curved space, a root unwitnessed);
- a manifest signed by the sitting reserve is sent: granted, or refused by
  a name that is the court's standing (`Short`, `Granted`, `InFlight`,
  `NoNewClosures`); a refusal that names the house's own act (`Unsigned`,
  `NotReserve`, `NotAUniverse`, `NotFounded`, `Malformed`) fails;
- the universe is read back, and must read as originated, in the geometry
  and parent face its origin stated; the endowment is read;
- the house posts its seats, reads the listing back equal to the post, and
  reads its mail at the relay's standing.

Each finding is `Passed`, `Failed` with its reason, `Unread` (no task to
solve, or a hypha that predates the act), or `Deferred` with the door's
deficit (§5): a client conforms where it declared a profile, every MUST
act of its profiles passed, and none failed. Run again with the same voice,
the kernel suite reads the domain, reserve and origin it left and conforms
again.

## 5. Deferral (**Built**)

A hypha whose worker pool is full answers every act with one reply, the
**deferral**: nothing was ruled and the act was not read. Every client, of
either profile, MUST recognise a deferral before it decodes a reply, MUST
never read one as a reply that did not decode, and MUST speak the act again
later.

Decoded, a deferral is the outcome reply (`decode_outcome_reply`) with:

| Field | Value |
|---|---|
| code | the pending code, `PENDING_CODE` = 2 |
| height | 0 |
| deficit | the door's reserve deficit on the lanes S, G, T, H: four `u64`, any values |
| taught | none (length 0) |
| after | nothing |

It is 43 bytes. A pending outcome that carries a height, teaches, or has
bytes after it is an answer, not a deferral.

The SDK's `mycelium_sdk::deferral` carries it: `read_deferral(reply)`
returns `Deferral { deficit }` off a reply's bytes; `Session::speak`
recognises it itself and answers it as a `WouldBlock` refusal that
`deferral_of(refusal)` reads back; `PENDING_CODE`, `is_deferral`,
`deferral_lanes` and `encode_deferral` are the codec.

`check_codecs` checks the deferral for every declared profile as the
finding `DEFERRAL` (MUST): a deferral reads back with its exact deficit,
and no MUST act's reply decoder of a declared profile reads its bytes as a
reply. `run` reports an act the hypha defers as
`Finding::Deferred { act, deficit }`, never as a failure; it does not
retry, since the session exposes no measured round trip to pace a retry
by, and the suite is run again once the door has room.

## 6. How a client runs it

```sh
cargo build --release -p mycelium-sdk --example conformance --example house
target/release/examples/conformance --endpoint 127.0.0.1:7700 --home /tmp/conformance-voice
target/release/examples/conformance --endpoint 127.0.0.1:7700 --home /tmp/house-voice --profile kernel
target/release/examples/house /tmp/house-voice 127.0.0.1:7700
```

`conformance` takes `--profile mind` (the default), `kernel` or `both`,
prints the declared profiles' MUST and MAY lists, the in-process report and
the network report, and exits 0 where both conform. `house` is a minimal
kernel uplink on `mycelium-sdk` alone: it reads the Concordance's clause
register, signs it by reconstructing each fixture and presents the act,
reads the clock, founds its domain, and runs the kernel
profile. `scripts/quickstart` runs both profiles and the house against a
fresh three-hypha network.

A kernel built on the SDK speaks through `mycelium_sdk::house`, which
re-exports the house-side encoders, decoders and types: domain founding
and the reserve, bond and origin; the universe and its statements; the
endowment's manifest and grant; the house side of seats; laws verify and
the batch; the clock; the Concordance's clause register, the signing act
and the kernel's signing helper (`signing`); framing and `HyphaKey`;
and the wire modules `domain`, `universe`, `endowment`, `seat`, `atlas`,
`uplink` and `challenge` whole.

A client written on another stack pins a Mycelium tag, reads the statement
at that tag (from the SDK, or from a hypha with `ACT_LAWS` mode 6), takes
the profile it is, and proves each MUST act the same way: its encoder's
output decoded by the hypha's decoder, its decoder fed the hypha's replies,
compared as exact values. A binding in another language (MU-PRECURSORS
§4.3 P7, **Specified**) passes this read with exact values only.
