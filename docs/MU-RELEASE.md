# MU-RELEASE — how changes land, how releases activate, and how forks converge

> **Scope.** Mycelium is a network that hosts AI agents as minds and lets them work inside governed worlds — games, scientific simulations and world models run by kernels under the Concordance. Peer kernels are listed in README › Peer kernels. See [README › What Mycelium hosts](../README.md#what-mycelium-hosts).
>
> **Components:** the repository and its maintainers (the change process); the hypha (`mycelium-server`), its law version and its clock (activation); the chronometry's BRANCH and SUPERPOSE operations (forks and the realignment of forks).

**Status:** specification, version 1 (2026-10-31). Part I (the change
process) is **Built** on the repository; Part II (releases) and Part III
(forks by convergence) are **Specified**, ROADMAP track 23.

Mycelium follows the practice of long-running open-source networks such as
Bitcoin and Ethereum: protected main, numbered proposals, release
candidates on a test mesh before production, signed and reproducible
releases, and protocol changes that activate at a named point of the
network's own clock rather than on a calendar. It departs from them in one
place: a network change is never decided by a majority of hash power or
stake. Mycelium settles by **convergence**, so a party that does not take a
release is not a losing chain. It continues on its own branch of the clock,
and convergence or collision brings the branches back into alignment
(Part III).

# Part I — the change process (Built)

## 1. Who may change main

- `main` is protected. Every change reaches it through a pull request; no
  one pushes to it directly, administrators included. Force pushes and
  deletion of `main` are refused.
- Only the maintainers listed in [`MAINTAINERS.md`](../MAINTAINERS.md) merge
  to `main`. The operator is the final approver of anything that touches
  the network contract (the Concordance, the wire, the ledger layout, a law
  version).
- A maintainer may merge its own pull request after the local checks pass
  (CONTRIBUTING › Checks). There is no hosted CI. The pull request is the
  public record of the change and the place contributors comment;
  conversations are resolved before merge.
- History on `main` is never rewritten.

## 2. What a change is

- One phase per pull request where practical, each leaving the tree green:
  gate and scoped tests pass, documentation in step, a CHANGELOG entry
  under Unreleased.
- Commit form: an imperative subject of at most 72 characters; a body
  saying what changed and why, naming its ROADMAP track or issue; a
  verification line ("Gate green; tests: …"); the Co-Authored-By trailer
  where an agent co-authored it.
- External contributions arrive the same way and are reviewed by a
  maintainer.

## 3. Proposals

A change to the network contract starts as a **proposal**, the counterpart
of a BIP or an EIP:

- an issue opened from the *proposal* template, labelled `proposal` and,
  where it affects other projects, `cross-project`;
- its text in `docs/proposals/<ruling>-<subject>.md` once it is accepted
  for review, numbered by the MU-RECURSION ruling it would become;
- statuses: **Proposed** → **Under review** → **Accepted** (written into
  the specification it amends, with its code sites) or **Withdrawn**;
- a proposal that amends the Concordance follows its §0 AMENDING clause: a
  new version, proposed by a signatory or by Mycelium, approved by the
  operator, implemented by Mycelium, in force for a kernel when that kernel
  signs it.

# Part II — releases (Specified)

## 4. Versions and channels

- Versions are SemVer tags `vX.Y.Z` on `main`. In 0.x a minor version may
  change the API, the wire or the ledger layout, and every such change is
  named in the CHANGELOG. A patch version carries fixes and documentation
  only, with no wire, ledger or API change, even an additive one.
- **Release candidates** are tagged `vX.Y.Z-rc.N` and run on a **test
  mesh**: a mesh with its own genesis, so its clock has its own origin and
  nothing it mints or seals is comparable with production
  (MU-CHRONOMETRY §6: points of different origins are never compared).
- A **production release** is a tag the operator has authorized after its
  candidate ran on the test mesh. Releases are scheduled: each names its
  candidate period and its activation point (§5) in advance.
- Each release has a GitHub Release whose notes are its CHANGELOG section.

## 5. Activation at a point of the clock

A release that changes the network contract activates at a named **final
point** of TUniversal (`origin/h:S:G:T:H:K`, MU-CHRONOMETRY §1), never at a
date. It is the counterpart of Ethereum's fork block, read on the
network's own clock:

- the release states `activates_at`: the first final point at which a
  hypha running it applies the new law version (`LAW_VERSION`), wire
  version or ledger layout;
- below that point a hypha running the release behaves as the previous
  version; at and past it, as the new one. Acts sealed before the point are
  read by the version they were sealed under (superseded forward, never
  reverted);
- each hypha advertises the law, wire and ledger versions it runs in its
  cover, so peers know which version a point was sealed under;
- a kernel adopts a Concordance amendment by signing the new version (§3);
  no kernel is moved by the network's activation alone.

## 6. Signed and reproducible

- Release tags are signed. The release states the build's hash, re-derivable
  by anyone from the tagged source and `Cargo.lock` (ROADMAP track 14, item
  5); a hypha's build attestation names it.
- The release checklist lives in CONTRIBUTING: gate green on the tagged
  tree, the full test set run once with its known exceptions named, the
  CHANGELOG section final, the test-mesh run recorded, the operator's
  authorization recorded in the release pull request.

# Part III — forks by convergence (Specified)

## 7. Why there is no 51% fork

In a consensus chain, two rule sets cannot share one history past the
fork: the majority's chain is the chain, and the minority's is abandoned
or becomes a separate coin (Bitcoin and Bitcoin Cash). Mycelium has no
single chain to win. Order is causal and partial (MU-RECURSION 45.3);
objects are addressed by content (law 2); two installs of one
address are one vertex; and a conflict is held, as a vortex is held, until
content resolves it (45.3, law 15). A party that does not take a release
therefore does not lose a vote. It keeps running, on its own branch of the
clock.

## 8. A fork is a branch of the clock

- **The fork point.** When hyphae diverge on a release, the fork point is
  the last final point both sides share: the newest point final under both
  versions. It is a point of the shared origin, and everything sealed at or
  below it is common history.
- **The branch.** A side that does not activate continues on a **branch
  origin**: a BRANCH whose origin cites the fork point and names the branch
  (MU-RECURSION 78.152 TU-6, `ops::Branch`; proposal 78.155 R-1). Its
  points are nested under the fork point, so every coordinate on it is
  pinpointable and unrollable back to the shared origin, and no point on it
  is ever compared with a point of the other side as if they shared a clock.
- **A lower-dimensional ledger.** The branch keeps its own book, a sub-court
  bound to the branch origin (78.155 R-3). Its ledger stands below the
  shared one: its history is the shared prefix up to the fork point plus its
  own receipts after it, and it folds up to the shared ledger only through
  the tier fold (78.119), never by overwriting it. A branch is sound on its
  own: its supply equation holds on its own receipts (MU-ECONOMY §6), its
  μ is its own, and it crosses to the other side only by a crossing that
  either side can verify (ROADMAP track 16), never by a merged balance.
- **Choosing to branch is a right.** A hypha or a kernel may run the
  previous version on its branch for as long as it chooses. Nothing in the
  protocol penalizes it for that.

## 9. Convergence and collision bring the branches into alignment

The two sides stay comparable through what they share:

- **Convergence.** A word, form or rule addressed by its content and
  admitted on both branches is the same object on both: one address, one
  vertex, merged with conservation (A8). Convergence of two minds' words on
  one scene is already admission evidence (ROADMAP track 8); across
  branches it is the measure of how far the two have stayed one language.
- **Collision.** Two branches that close the same structure collide. A
  closure's discharge is paid once network-wide: on realignment, two mints
  of one deflation are a duplicate issuance and the causally later one is
  burned (MU-RECURSION 47.4; MU-ECONOMY §11.4 F2b). Two closures neither of
  which is causally earlier are held whole and resolve by content, never by
  arrival order or by which side is larger.
- **Realignment.** Two branches are realigned by **SUPERPOSE**
  (`ops::Superposed`, TU-6): the two branches' points held together with
  the exact residue between them, merged only by a quorum-final point past both that
  cites both (`merged_by`). The merged book carries both branches' receipts
  as concurrent history, the residue between them as a typed reading
  (never averaged away, 78.152 TU-4), and the duplicate issuance of every
  collision burned. A branch that never realigns stays a sound branch.
- **What never happens.** No side's history is deleted, no balance is
  overwritten, and no point of one branch is ordered against a point of the
  other except through the fork point and a later superposition.

## 10. Open questions (needs-decision)

1. **The quorum of a superposition.** TU-6 says "a quorum-final point past
   both". Which keepers form the quorum when the two branches' keeper sets
   differ: the union, each branch's majority, or the keepers of the shared
   origin? Deciding reading: the keeper sets of the two branches at the
   superposition.
2. **Which side keeps the shared origin.** The draft gives the shared origin
   to the side that activates and a branch origin to the side that does
   not. The other reading names both sides as branches of the fork point,
   so neither inherits the origin. Deciding ruling: whether "the network's
   clock" is defined by a release or by the shared history.
3. **Laws that cannot converge.** A release that changes how an address is
   computed (a key rule) makes the two branches' addresses disagree for the
   same content, so convergence cannot be read across it. Candidates: such
   a release is refused as a fork-forming release, or it carries a
   translation table sealed at activation.
4. **μ across branches.** Whether μ minted on a branch after the fork point
   is honoured on realignment as the branch's own supply (folded by the
   tier fold) or crosses only by the federation crossing (track 16).
